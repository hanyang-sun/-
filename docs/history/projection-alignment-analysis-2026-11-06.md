# 投影贴合问题：成因、评估标准与校正方案

状态：方案 B 已实现，图像验证结果见文末；亮度、模糊和硬件标定建议尚未实施
日期：2026-11-06
适用：`真实投影` 分支（`SimulationProjectedLight` + `Resources/ProjectedLight/*.shader`），Unity 6000.3.24f1，Built-in 渲染管线

## 摘要

校正前，虚拟投影仪把内容按正交俯视图生成，再以透视光路回投，积木顶面会出现向中心收缩的偏移。下文的“现状”光路和代码片段保留为修复前后对照；当前已改为方案 B。

该偏移由投影几何自然产生，但本项目最终落地真实硬件、由人观看，**观众会把它读作“系统没对准”，而不是“投影仪的物理特性”**。因此判定为“未做部署校正”，而非需要保留的真实性。

采用**投影仪视角烘焙**（方案 B）：内容相机与投影仪共用位姿、视场角、裁剪范围和实际矩阵，按已确认布局的目标表面生成预校正输出。保留原有遮挡和表面反射近似；几何未知、目标超出光锥或被遮挡时，不能保证对齐或可见。

---

## 1 现象

在 10×10 棋盘上，投影图案（格点、角色高亮、变更环）与积木顶面不对齐：

- 棋盘中心附近几乎看不出偏差
- 越靠边缘偏移越大
- 桌上无积木处（`y = 0`）没有偏移

---

## 2 评估标准：给人看，还是给相机看

投影的消费方有两个，优化方向不同：

| 维度 | 相机 / 算法 | 人眼 |
| --- | --- | --- |
| 在乎 | 像素可分、颜色可判 | 图案是否对齐、亮不刺眼、闪不闪 |
| 正交还是透视 | 影响采样坐标 | 投影产生的尺度、形变和对齐差异会影响观感 |
| 高度偏移 | 会影响采样位置、颜色和占用判定 | 会被读作“没对准” |

本项目最终以真实硬件落地，观众是人。由此确定分工：

> **几何要校正（服人），光学要保留（像光），采集参数独立（服算法）。**

---

## 3 成因

### 3.1 修复前的光路

`SimulationProjectedLight` 的实现分四步：

1. **内容烘焙**：正交俯视相机 `(5, 20, 5)`、`orthographicSize = 6`、只拍 layer 31，把格点/高亮/变更环烘成 512² 输出图
2. **光路映射**：`view = Scale(1,1,-1) × TRS(projectorPosition, projectorAngles)⁻¹`，`vp = GetGPUProjectionMatrix(Perspective(fov,1,0.1,50)) × view`
3. **遮挡**：用同一 VP 把接收物画进 512² 深度图（`-viewZ / Far`）
4. **着色**：`albedo × image × incidence × attenuation × strength`，加色混合

问题出在第 1 步：**内容相机是正交的，图案因此被定义在桌面平面上**；而第 2 步的投影是透视的。

### 3.2 数值推导

投影仪位于 `(5, 14, 5)`，积木顶面 `y = 1`，桌面 `y = 0`。

积木顶面上的点 `W = (x, 1, z)` 所在的光线，继续延伸到桌面 `y = 0` 的交点：

```
t = (14 − 0) / (14 − 1) = 14/13 ≈ 1.0769
桌面交点 = 5 + (14/13) × (x − 5)
```

即：**积木顶面看到的是“更靠外 7.69%”那个位置的图案**。偏移量随距离线性增长：

| 距投影仪正下方的距离 | 偏移（格） |
| --- | --- |
| 1 | 0.077 |
| 3 | 0.231 |
| 5（棋盘边缘） | **0.385** |

注意，上表是“给定表面点反查桌面纹理”的坐标差，不是图案实际落点的位移。已知桌面图案距中心 `d`，投到高度 `h` 时其距中心变为 `d × (H-h)/H`，因此实际向内位移为 `d × h/H`。`H=14,h=1,d=5` 时约 **0.357 格**，而不是 0.385 格；对应尺寸也会收缩。7.69% 是逆映射尺度差，不能直接当作图案中心相对一格宽的误差。

### 3.3 为什么“物理正确”并不等于“应该保留”

偏移在单台真实投影仪上确实存在，但真实部署不会接受它：

- 投影映射（projection mapping）的全部意义，就是按现场几何预畸变内容
- 观众扫一眼桌子会发现“中间准、四角不准”，这比整体平移更像故障
- 部署验收里“图案与物体对不齐”属于缺陷，不属于艺术效果

结论：**保留偏移 = 没做部署校正；校正后的投影才是真实部署的样子。**

## 4 方案对比

| 方案 | 做法 | 积木对齐 | 桌面影响 | 改动量 | 真实对应 |
| --- | --- | --- | --- | --- | --- |
| A 平面反畸变 | 正交尺寸缩到 `6 × 13/14`，标定在 `y = 1` | 仅该高度 | 桌面图案外扩约 7.7% | 小 | 单一高度校正 |
| **B 投影仪视角烘焙** | 内容相机与投影仪同位姿、同 FOV，图案位于已知目标表面 | 已知高度且光路可达时 | 默认正投桌面映射基本保持 | 相机、内容高度、测试及场景配置 | 投影映射内容管线 |
| C 深度感知 UV | 着色时把采样点推到标定平面再算 UV | ✅ | 可调 | 约 6 行着色器 | 带几何校正的投影仪 |
| 现状 | 正交相机 | ❌ 最大 0.385 格 | — | 0 | 未校正的投影仪 |

方案 A/B 可以保留原有光路和遮挡测试。方案 C 若直接按接收点改写 UV，可能让同一条光线的采样依赖接收深度，不能未经验证便认为与真实单张投影输出等价；本轮不采用 C。

方案 C 属于在光路里补偿，投影仪本身并不知道几何；方案 B 与 A 都是“改幻灯片”，与真实投影映射的做法一致。**推荐 B**。

## 5 推荐方案 B：投影仪视角烘焙

### 5.1 原理

```text
内容相机 ≡ 投影仪
    → 烘出的图已包含预畸变
    → 投影仪把这张图投回去，每个点回到它被拍下的位置
```

图案必须先放在目标表面。校正前的角色面片在 `1.006/0.006`，章鱼脸在顶面以上 `0.04`，其他动态图案还有不同抬高值。现已删除这些旧显示偏移：章鱼脸和角色标记按单层顶面 `y=1` 放置，地面道路/触手等按 `y=0` 放置，叠放用透明绘制排序。已知目标高度、光路可达且标定一致时，回投才能对齐；当前没有多层识别。

### 5.2 代码改动

`SimulationProjectedLight.EnsureResources()` 中，内容相机由

```csharp
contentCamera.orthographic = true; contentCamera.orthographicSize = 6;
contentCamera.aspect = 1;
contentCamera.transform.SetPositionAndRotation(new Vector3(5, 20, 5), Quaternion.Euler(90, 0, 0));
```

改为

```csharp
contentCamera.orthographic = false;
contentCamera.fieldOfView = fieldOfView;
contentCamera.aspect = 1;
contentCamera.nearClipPlane = 0.1f;
contentCamera.farClipPlane = Far;
contentCamera.transform.SetPositionAndRotation(projectorPosition, Quaternion.Euler(projectorAngles));
```

并在每次烘焙前同步位姿（`projectorPosition / projectorAngles / fieldOfView` 在运行时可变）：

```csharp
contentCamera.fieldOfView = fieldOfView;
contentCamera.transform.SetPositionAndRotation(projectorPosition, Quaternion.Euler(projectorAngles));
contentCamera.Render();
```

### 5.3 为什么台面观感不变

`FOV = 46.39718° = 2·atan(6/14)` 是按投影仪高度 14、覆盖 12×12 反推出来的。因此在默认垂直正投、`y = 0` 平面上，两套几何覆盖基本一致；栅格化和过滤可能有像素差异，不承诺逐像素相同。改变投影仪位姿后，方案 B 会重新生成预校正输出，仍以目标表面对齐为目的。

### 5.4 对照与实际实现

讨论曾建议保留以下模式枚举，但本轮未引入，避免长期维护旧烘焙分支：

```csharp
public enum SlideMode { FlatTable = 0, ProjectorBaked = 1 }
```

角色内容默认全部采用透视烘焙。`CalibrationPattern` 测试入口仍直接输入固定幻灯片，所以其高度偏移与移动光斑测试继续有效。实际回投与深度矩阵直接取内容相机的 `worldToCameraMatrix`、`projectionMatrix`，不再独立拼装另一套投影矩阵。

## 6 观感配套：不只是对齐

几何对齐只是第一眼的问题；让人看着舒服还需要以下调整。

| 项 | 现状 | 问题 | 建议 |
| --- | --- | --- | --- |
| 亮度均匀 | `attenuation = min(1.5, 196/d²)` | 角落明显偏暗，像灯泡而非投影 | 加归一化 gain，按到接收面的距离补偿；目标中心/角落差 ≤ 25% |
| 边缘羽化 | `blurPixels = 0.5` | 边缘出现硬阶梯 | 实机建议 2–3 px，或换高斯核；宁可略糊，不要硬边 |
| 亮度上限 | `lightStrength = 1.3` | 白光图案过曝，洗掉积木本色 | 按实测降到刚好不发白；任通道不饱和（< 0.98） |
| 黑场 | `blackLevel = 0` | 实机黑场有残余光 | 用实拍黑帧填充，不能长期留 0 |
| 颜色 | 高亮用满饱和色 | 白墙发灰、红积木发黑，观众分不清是图案还是积木变色 | 饱和度降到 60–70% |
| 阴影方向 | 遮挡来自正上方投影仪 | 与场景左右白光方向不一致时画面显“脏” | 保持光源方向单一且自洽 |
| 闪烁 | 消隐取样会关投影 | 黑一下再亮 | 连续投影识别是独立后续课题；当前消隐策略保持不变 |

以上均为待验证建议，不是已实施参数或实机结论。2–3 px 模糊可能损失小图案细节，亮度补偿/黑场须实测；环境光与投影仪本来就可能具有不同方向，无需为了画面整洁抹除真实阴影。

## 7 验收清单

| 判据 | 目标值 |
| --- | --- |
| 图案中心与目标中心偏差 | 仿真实际 RGB 光斑测量 ≤ 0.02 格，覆盖中心/四角、正投/斜投和显式高度 |
| 中心与角落亮度差 | ≤ 25% |
| 图案边缘过渡 | ≥ 2 px 羽化，无硬阶梯 |
| 白光图案是否过曝 | 无通道饱和（< 0.98） |
| 帧间亮度波动 | ≤ 2%，无肉眼可见闪烁 |
| 斜投时图案可读性 | 纹样/文字仍可辨认 |

## 8 与识别链路的关系

本文不再对另一个识别分支的当前实现作未经核验的判断。当前 `真实投影` 分支由 `SimulationCameraCapture.ReadTopDown` 调用顶置相机 `Render()` 并读取 RGB：带投影采样会受到几何校正、亮度和模糊的影响，必须重新评价，不能保证准确率不变。干净采样使用统一消隐门，本轮不改采样间隔或消隐时长。

图案定位仍仅消费已确认布局；内容相机只拍图案层。源场景真实几何用于遮挡和接收光，不直接向识别器提供占用、颜色、ID 或高度。识别尚未确认移动时，图案仍可能留在旧位置。

## 附录 B 关键公式

```
偏移倍率            k = (h_projector) / (h_projector − h_surface)
                    = 14 / 13 ≈ 1.0769            // h_surface = 1

偏移量（格）        Δ(d) = d × (k − 1)
                    d = 5 时 Δ ≈ 0.385

表面光照贡献        L = albedo × image × saturate(N·L) × min(1.5, 196/d²) × strength
                    albedo = 材质 _Color × _MainTex
                    image  = 5-tap 模糊后的投影图案，lerp 到白场的黑电平修正

遮挡判据            eyeDepth > depth(uv) × Far + bias      → discard
```

## 本轮实现与验证

- 原地修改 `SimulationProjectedLight`、`ProjectionSimulator`、`SimulationBattleOverlay`，同步清理场景与安装菜单中的 `surfaceOffset/ringHeight`。无新增产品文件、模式开关或依赖；材质光强、模糊、识别采样和消隐参数不变。
- `PhysicalProjectorChecks` **75 项通过**。45 个 RGB 光斑测量点覆盖中心/四角、0/1/2 三种显式高度，以及默认正投、斜投、斜投中修改 FOV。最大中心误差 **0.01246 格**，低于 0.02 格。为完整观察高处角点，仅该光学 fixture 暂时扩大顶置相机 FOV，测试结束恢复；产品相机参数不变。
- 固定幻灯片仍有高度位移；黑场、表面颜色反射、投影遮挡和干净 RGB 100/100 检查通过。章鱼脸目标高度为 1，使用已确认布局。
- 测量期间发现 `GetComponentsInChildren` 仍可能返回停用根节点本身的 Renderer，导致直接命令绘制产生幽灵遮挡。接收物收集现在显式排除 `!activeInHierarchy`；回归确认停用挡光积木后同一点光照恢复。
- 实时 RGB/战斗更新 **146 项通过**，双窗口消隐 **35 项通过**（断言数随观察帧数变化，覆盖停止/禁用、F8 带投影、相机异常与恢复），纯逻辑 **1195 项通过**。证据在本机 `.scratch/dual-window/run-20261106-alignment/`，不将截图提交到仓库。
- 此结果是 Unity 仿真验收，不代表实机标定、连续投影识别准确率或多层识别已完成。

随后已将 Brick2Life 的光度恢复算法接到 C 的实际 RGB，采用固定识别相机曝光和独立灰参考标定；投影光强/光路不变。整合后的几何 45 点最大误差 0.01348 格，仍达标。后续两种模式及结果见 [当前验证摘要](../verification/current-simulation.md)，上文首轮数值保留为历史记录。
